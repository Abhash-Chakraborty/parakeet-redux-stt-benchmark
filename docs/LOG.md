## 2026-10-05: Phase 0 (feasibility gate)

- **21:05** Project skeleton created. Three isolated uv venvs (Python 3.12.13): `envs/tcpp` (transcribe-cpp 0.3.1), `envs/photon` (moondream 2.6.1, kestrel 0.9.1, kestrel-kernels 0.7.4, torch 2.14.1), `envs/cloud`.
- **21:10** transcribe-cpp backends detected: `Vulkan0` = AMD Radeon iGPU, `Vulkan1` = GTX 1650 (4 GB), `CPU` (ggml-cpu-haswell = AVX2 kernel). The iGPU is excluded from the study; "GPU" always means the GTX 1650.
- **21:11** Free RAM at idle with the user's normal apps open: **2.7 GB of 15.3 GB** (browser, Node, WSL/Docker, several editor sessions). Timed runs need these closed; see Controls.
- **21:12** **Parakeet Redux fails on Windows.** `md.photon(..., device="cpu")` raises `NotImplementedError: ... the path in use here is 'scalar'`. `kestrel_kernels._cpu.gemm_isa_available()` reports avx512vnni=False, avxvnni=False, **avx2=False**, although the Ryzen 5 5600H supports AVX2.
- **21:2x** Forcing the path with `kestrel_kernels.ternary.set_gemm_isa("avx2")` loads the model, but the first matmul raises `ValueError: no 'avx2' matrix-multiply path on this machine` (`results/redux_avx2_probe.txt`). Conclusion: the Windows wheel of kestrel-kernels 0.7.4 does not ship or enable the AVX2 ternary GEMM. Photon's CUDA path requires Ampere+ (docs), so the GTX 1650 is out of support too.
- **Decision (deviation D1):** run Parakeet Redux in a Linux container (Docker Desktop, WSL2 backend) on the same CPU, per the plan's fallback. To quantify VM overhead, one transcribe.cpp model (parakeet-tdt-0.6b-v3 Q8_0) is also run on CPU inside the same container, and its speed is compared with the native Windows run.
- **21:3x** transcribe.cpp smoke test on JFK (11 s): moonshine-base F16, parakeet-tdt-0.6b-v3 Q8_0, parakeet-unified-en-0.6b Q8_0 all produce the correct transcript on CPU and GPU. The first GPU call per process takes 4 to 8 s (Vulkan pipeline compilation); later calls take about 0.3 s. Cold vs warm latency is therefore reported separately. (These timings overlapped background downloads; smoke only, not results.)
- **21:3x** Linux container `stt-photon:1` (python:3.12-slim, torch 2.14.1+cpu, moondream 2.6.1, transcribe-cpp 0.3.1; `docker/Dockerfile.photon`): `kestrel_kernels._cpu` reports **avx2=True** (avx512vnni/avxvnni False), conformer ops also avx2. Redux transcribes JFK correctly: load 8.7 s, 1.0 to 1.1 s per 11 s clip on 4 vCPUs. So the missing AVX2 path is specific to the Windows wheel, not this CPU.
- WSL2 is capped by the user's `~/.wslconfig` at `processors=4`, `memory=6GB`. The protocol pins CPU runs to 6 threads, so this cap must be resolved before timed runs (see next entry).
- **Data built.** A: 6 YouTube clips (`scripts/prepare_youtube.py`, manual caption tracks only), 20.7 min. B: 50 utterances; AMI shard 5 held only 2.1 to 2.7 s utterances, so the sampler now walks to longer shards until ≥30 candidates are in 4 to 25 s (AMI used shard 3). C: 10 noisy clips. B2: 12 Speech Accent Archive speakers via Kaggle (`scripts/prepare_accent.py`). D: script and recorder ready, waiting for the user.
- **Chunker fix (before any run).** The first chunker hard-split VAD regions at exactly 30 s, leaving 0.1 s slivers and mid-word cuts. It now cuts 10 to 28 s after the previous cut, at the longest VAD pause, or else at the quietest 200 ms. Result: 140 units, 33.2 min, chunk lengths 6.8 to 28.6 s.
- **Speed subset reduced** (before any timed run) from all of B to 4 clips per B group (20 clips), because Whisper large-v3 runs below real time on CPU (~16 s for the 11 s JFK clip, smoke test).
- **WSL cap raised (user-approved).** `~/.wslconfig` backed up to `~/.wslconfig.stt-benchmark.bak` (copy in `results/wslconfig.original.bak`), set to `processors=12`, `memory=8GB`, then `wsl --shutdown`. Docker now reports 12 CPUs and 8.3 GB. **To restore after the benchmarks**, the original file goes back and WSL restarts.
- Parent-side CPU% read 0 because the venv `python.exe` on Windows is a launcher whose child is the real interpreter, and child handles were recreated on every sample. Fixed by caching psutil handles per pid. Parent and in-worker readings now agree within 2% (moon_f16 CPU: 560% vs 566%).
- **21:4x** Cloud smoke test on JFK: OpenAI `gpt-transcribe` 2.5 s, ElevenLabs `scribe_v2` 1.2 s (`tag_audio_events=false` so "(laughter)"-style tags are not scored as insertions), Vercel to `google/gemini-3.5-transcribe` 3.9 s. All transcripts correct. Cloud runs use default account terms (no ZDR requested), which is what a typical user gets.
- **21:53** Vercel's Gemini STT is limited to **5 requests/min per team**. The first run hit HTTP 429 and skipped units after backoff. It was restarted with `--min-interval 13` (resumes and retries skipped units). Its latency figures come from the paced run and are unaffected by the cap.
- Photon thread control: `md.photon(..., cpu_threads=N)` sizes both torch and the native kernel pool. Without it, Photon uses min(physical cores, 4) for ternary models, so the 4-thread Redux config equals its out-of-the-box default.
- **22:01 Deviation D2: subset A peak normalization.** Photon rejected `A_ted_clean__c02` ("out-of-range float32 sample"). 31 of 66 A chunks have float samples above 1.0 (inter-sample overs from YouTube's lossy stream; the Tharoor clip peaks at 1.475, the street clip at 1.86). transcribe.cpp accepted them unclipped, but `run_cloud.py` clipped them when writing 16-bit WAV, so subset A inputs were **not identical across systems**. Fix: one linear gain per parent clip (peak scaled to 0.99; chunk boundaries unchanged; B, B2 and C untouched since they never exceed 1.0), then **all systems rerun subset A**. The scorer now lets the newest file win per unit (by mtime), so the superseded A outputs stay on disk for audit but are not scored.
- **22:1x** Determinism check (PROTOCOL 6.6): 10 B clips rerun on CPU give text **identical** to the GPU accuracy pass for all 6 transcribe.cpp systems, and a Redux rerun is identical to its first pass (10/10 each). Accuracy results therefore hold for both devices.
- **22:2x** Whisper large-v3's high deletion rate on A (7.0% on the podcast clip) is verbatim-vs-clean style, not skipped audio: it omits repeated fillers ("you know", "so"), while the en-IN caption track is verbatim. Per-chunk word counts confirm every chunk was transcribed. Reported as a threat to validity (reference style), not a model defect.
- **22:3x** Subset D changed (before any recording) from 15 single sentences to 4 short paragraph scripts (~25 s each), at the user's request: closer to how Handy is used (a few sentences per dictation) and each paragraph is one exact reference. Same content (names, numbers, tech terms, punctuation).
- **22:4x** Speed runs started on a quiet machine: Handy and browser closed, AC power, 8.6 GB RAM free, user away. Own-voice set D recorded (4 paragraphs, 131 s, peaks 0.29-0.39), split into 7 units; non-D units verified byte-identical in units.csv. User reported some fumbles while reading; see the verbatim-reference entry below.
- **22:4x** Own-voice fumbles (user reported): deviations where >=5 of 6 strong local models (all but Moonshine) agree on the same everyday-word change are treated as what was actually said -> data/own_voice/verbatim.txt (good, changes, services, be joining, Celsius, egg, banana, dropped before/we/the/a/and, Thank you). Candidates: results/own_voice_fumble_candidates.json.
- **23:49** Speed runs complete: 16/16 configs, no failures (results/speed_run.log). User consented (22:4x) to sending subset D to the cloud models; sent after timing finished so uploads could not perturb timings.
- **23:5x** Speed results (results/metrics_speed.csv): VM overhead calibration came out **negative**: tdt_q8 CPU RTFx 10.72 in the Linux container vs 9.26 natively (+16%), so the Linux CPU build is faster, not slower.
